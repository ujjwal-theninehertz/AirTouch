AirTouch project blueprint

AirTouch lets people use an Android phone without touching the screen. The front camera watches the user's hand, MediaPipe finds 21 landmarks on it in every frame, Kotlin logic turns their movement into gestures, and an AccessibilityService performs the matching swipe, tap or navigation in whatever app is open. This page is the plan to build it, written before any code.

First device: Redmi Note 8 Pro · Android 11 · MIUI 12.5 Helio G90T · Mali-G76 MC4 · 1080 × 2340 Kotlin · CameraX · MediaPipe · AccessibilityService Offline · no backend · $0 tooling

01 · Recommended architecture

One process, five layers, no server

Each layer is its own component with a typed output, so detection, classification, mapping and screen control can be tested and replaced separately. Everything runs on the phone. Camera frames stay in memory and are never stored or sent anywhere.

  1. AD-1

    Run the live pipeline inside the AccessibilityService

    Android binds this service for as long as the user keeps AirTouch enabled, so detection keeps running while they move between Instagram, YouTube and other apps. Google's open-source Project Gameface uses the same pattern: CameraX and MediaPipe running inside an AccessibilityService. AirTouch adds one documented safeguard. Detection always starts from a visible surface (the app, the Quick Settings tile or the notification), and the service then calls startForeground() with type camera. That foreground service keeps camera access after the user leaves the app and shows a notification with Pause and Stop.

    Fallback if a device refuses: a separate camera foreground service started from the app, sending events to the AccessibilityService over an in-process event bus. The Phase 0 spike decides which one to use, on the Redmi Note 8 Pro and on one Android 14+ phone.

  2. AD-2

    Keep the gesture engine in pure Kotlin, in its own module

    The gesture-engine module has no Android imports. Unit tests replay recorded landmark traces on a laptop, so thresholds are tuned in seconds without a phone, and the build stops anyone from adding a platform dependency.

  3. AD-3

    Recognise gestures with rules first, behind an interface

    Swipes, pinch and fist are classified with geometry and timing rules: deterministic, explainable, and they need no training data. They sit behind a GestureClassifier interface, so a trained model can replace or join them later without touching the other layers.

  4. AD-4

    One physical gesture fires at most one action

    A safety guard sits between the classifier and the mapper: an arming state, confidence and hand-size gates, voting across frames, a cooldown, and suppression of the return stroke that follows every swipe.

  5. AD-5

    Tap with an air cursor and confirm with a pinch

    Fingertip position alone is too unsteady to pick a tap target. AirTouch shows a smoothed cursor and taps when the user pinches. The tap lands where the cursor was about 120 ms before the pinch began, because closing the fingers pulls the index tip off target.

  6. AD-6

    Draw feedback as an accessibility overlay

    TYPE_ACCESSIBILITY_OVERLAY needs no "Display over other apps" permission, and Android 12+ treats it as trusted, so injected touches still reach the app underneath.

  7. AD-7

    Stay offline by design

    The merged manifest declares no INTERNET permission. The models ship inside the APK, settings live in Jetpack DataStore, and dependencies are wired by hand in an AppGraph instead of a DI framework.

  8. AD-8

    Hands or face, one at a time

    AirTouch is driven either by hand gestures or by face gestures (quick nods and turns, eyes closed, eyebrow raises, a kiss), never both at once. Turning on face gestures turns hand gestures off, and turning on hand gestures turns face gestures off. The choice is one DataStore setting, gestureMode, with hands as the default. Only the chosen mode's MediaPipe model is loaded (Hand Landmarker or Face Landmarker), so it gets every camera frame and the GPU to itself, and one input can never set off the other, such as a hand raised in front of the face or a nod during a flick. Hands-free mode and practice mode both follow the setting, and changing it restarts a running session in the new mode.

    Consequences: a ringing call is answered with ✋ and rejected with ✊ in hand mode, and with the left or right eyebrow raised twice in face mode. In face mode, pause and resume come from the notification, since 👎 is a hand gesture. The status pill and the notification name the active mode.

02 · End-to-end workflow

From one camera frame to one screen action

Every frame runs the left column. Only a steady, armed hand reaches the right column, and only a gesture that passes every guard reaches the screen. Every other path drops the frame and waits for the next one, so the loop never blocks.

06 · Gesture design and accidental-action prevention

Six gestures, one action each

Landmark x is mirrored for the front camera, so "left" always means the user's left. Distances are divided by hand size, so the same rules work at 30 cm and at 80 cm.

Arming state machine

Tapping a precise spot: air cursor with pinch-to-confirm

1 · Enter

Point with the index finger for 0.5 s, or switch from feed mode in the HUD. A cursor appears.

2 · Aim

The cursor follows the smoothed index tip. The middle 60 % of the camera view maps to the full screen, so the arm never has to reach the edges.

3 · Confirm

Pinch. The tap lands where the cursor was 120 ms before the pinch began, and the ring turns solid as it fires.

4 · Cancel

Open the palm or lower the hand out of view. Nothing is dispatched.

Planned for v1.1: snap the cursor to the nearest clickable element. It needs window-content access, so it stays off by default. A 3 × 3 zone grid is the fallback for users who need larger targets.

07 · Permissions and platform constraints

What Android allows, version by version

Android does not behave the same on every version, and Xiaomi adds rules of its own on top. The plan works within each limit below. The Redmi Note 8 Pro stops at Android 11, so the newer rules still have to be tested on other phones.

What is feasible

FEASIBLE

Standard, documented APIs

  • 21-point hand tracking on the phone
  • Swipe, pinch and fist from custom rules
  • Swipe, tap, double-tap, long press via dispatchGesture
  • Back, Home, Recents, notifications
  • Overlay HUD and cursor with no extra permission
  • Offline use, local settings
  • Start, pause, stop from app, notification, tile
NEEDS DEVICE TESTING

Works, but varies by phone

  • Camera kept alive by the AccessibilityService on MIUI and other OEM skins
  • One swipe = exactly one Reel or Short as apps update
  • 15 fps on the Helio G90T; CPU vs GPU
  • Accuracy in dim light and backlight
  • Landscape, tablets, foldables, split screen
  • Quick Settings tile start on Android 14+
NEEDS A WORKAROUND

User action or a design change

  • Accessibility must be switched on by the user
  • Android 13+ sideloads: "Allow restricted settings"
  • MIUI autostart, no battery restrictions, lock in Recents
  • Another app takes the camera: suspend and retry
  • Notification can be swiped away: tile and gesture controls
  • Imprecise taps: cursor plus pinch
NOT FEASIBLE OR OUT OF SCOPE

By platform rule or by choice

  • Control with the screen off or locked
  • Apps that refuse accessibility input (some banking, payment, DRM)
  • Sharing the front camera with another app
  • Starting the camera at boot (blocked on Android 15+)
  • Exact taps from raw fingertip position
  • iOS

Settings the user has to change by hand

  1. 01Turn on the accessibility service. Settings → Accessibility → Downloaded apps (MIUI: Installed services) → AirTouch. An app cannot do this for the user. For development: adb shell settings put secure enabled_accessibility_services <package>/<service>.
  2. 02Android 13+, APK installed from a browser or file manager: App info → ⋮ → Allow restricted settings, then repeat step 1. ADB installs and Android 11 phones are not affected.
  3. 03Battery. Android 12+: App battery usage → Unrestricted. MIUI: Battery saver → No restrictions.
  4. 04Xiaomi only: Security → Autostart → on, and lock AirTouch in Recents so cleaning Recents does not kill it. Samsung, OPPO and vivo have similar switches; the setup wizard shows the right one for each brand.
  5. 05Android 12+: keep the Camera access quick toggle on. If it is off, frames arrive black and AirTouch shows "Camera blocked".

Limits on controlling other apps

Camera is exclusive

Only one app can use the front camera, and the app on screen wins. Instagram's Story camera or a video call suspends AirTouch. It resumes when the camera is free again.

Some apps reject accessibility input

Some banking and payment apps block or warn about third-party accessibility services. Views marked data-sensitive (Android 14+) respond only to verified accessibility tools. These apps go on the default block list.

App updates change gestures

A swipe that advances a Reel today may behave differently after an Instagram update. Stroke length and speed live in per-app profiles, so they can be retuned without new code.

Store and install rules

Google Play needs the Accessibility declaration form and an in-app disclosure. Since Oct 2025 it bans accessibility use that acts on its own, but user-triggered fixed rules like AirTouch's remain allowed. Android developer verification started on 30 Sep 2026 in Brazil, Indonesia, Singapore and Thailand, for installs from seven app stores only, with a global rollout planned for 2027. ADB installs are not affected, and a free account covers up to 20 test devices.

10 · Proposed project structure

Two modules, one package per layer

The gesture-engine module is plain Kotlin, so the build itself stops Android code from leaking into recognition logic. Packages in app follow the architecture layers. No files are created yet. com.airtouch is a placeholder for your own reverse-domain ID.
